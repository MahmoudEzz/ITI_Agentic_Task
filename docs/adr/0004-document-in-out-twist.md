# ADR-0004: T6 twist — OCR and document generation approach

## Status

Accepted — implemented and live-verified end-to-end in Phase 5: OCR against all 5 scanned-CV fixtures, `generate_report` producing real DOCX/PDF from a real finalized run, and the full FSM driven from a real screening run through approval, report generation, and `COMPLETE` via `npm run screen`.

## Context

T6 requires OCR of scanned PDFs with confidence handling, and a professionally formatted generated document (DOCX and/or PDF) with citations and tables. For D6, this maps naturally onto: some candidate CVs arrive as scanned PDFs with no text layer, and the shortlist deliverable itself should be a formatted report, not a chat transcript.

## Decision

**OCR**: `tesseract.js` (pure JS/WASM, fully offline, free). Pipeline: attempt native text-layer extraction first (`pdf-parse`); if extraction yield is below a chars-per-page threshold, flag the document as scanned (`PdfExtractor`'s `needsOcr`), rasterize its pages, and OCR each page image, which yields a per-page mean confidence score. Chunks produced from an OCR'd page carry that page's `ocrConfidence` and an `ocrVersion` stamp (Phase 5): below 70 is flagged `low_confidence` and still surfaces in citations with a visible warning rather than silently trusted; below 40 is flagged `unusable` and excluded from `get_candidate_chunks` (the Evidence Extractor's only tool), forcing human review — it still exists in the DB for audit, just never reaches automatic scoring.

**Rasterization amendment (Phase 5, supersedes the original `pdftoppm` plan)**: rendering is `pdfjs-dist` + `@napi-rs/canvas`, both pure JS/prebuilt-binary npm packages, not `pdftoppm`/poppler-utils. This was discovered mid-Phase-5 to be strictly better for this project: no native binary to install (poppler-utils/Homebrew were unavailable on the local dev Mac, which would have forced Docker-only verification for every OCR change), works identically on the host, in CI, and in the Docker image, and removes `poppler-utils` from the Dockerfile entirely (only `chromium`, for Puppeteer, remains). Verified against all 5 real scanned-CV fixtures before adopting — see the Consequences section for actual confidence values. This is the same kind of correction as ADR-0005's `zod-to-json-schema` → `z.toJSONSchema()` swap: a documented improvement on the original plan, not a silent edit.

**Document generation**: `docx` (dolanmiu/docx) produces the primary DOCX report — a scoring matrix table per candidate/competency, citations back to `sourceChunkId`/document/page, and the interview-probes section. A **Puppeteer HTML→PDF** path renders the same report content as a PDF twin. Both formats are generated only after the hiring manager approves or edits-and-approves the shortlist — `generate_report` is a gated write tool, never executed speculatively.

## Alternatives considered

- **A cloud OCR API (e.g. Google Vision, AWS Textract)** — likely higher accuracy, but reintroduces a paid/hosted dependency the brief explicitly designs against, and moves candidate PII off-infrastructure for a capability that has a free, offline equivalent. Rejected in favor of `tesseract.js`; the accuracy trade-off is disclosed candidly in `docs/EVALUATION.md` and `docs/SECURITY.md` rather than hidden.
- **DOCX-only output** — would satisfy the "DOCX/PDF" wording literally with less effort; superseded by a deliberate decision to build both formats from one report-content model, since the incremental cost of an HTML→PDF render on top of an already-structured report is modest.
- **A dedicated PDF library (pdf-lib) instead of Puppeteer** — pdf-lib gives lower-level control but requires hand-laying-out tables/text; Puppeteer-from-HTML reuses ordinary CSS for table/citation formatting, which is faster to build and easier to keep visually consistent with the DOCX version's structure.
- **`pdftoppm` (poppler-utils) for rasterization** — the original plan; rejected mid-Phase-5 (see the amendment above) once it was confirmed to work fine as a native-binary dependency but to require Docker for every local verification cycle, which the pure-JS alternative avoids entirely at no accuracy cost.

## Consequences

- OCR confidence thresholds (70/40) are stated as provisional in `docs/BRD.md` until real OCR output exists on the synthetic scanned-CV fixtures (Phase 5); the tuning process, not just the final numbers, is documented.
- Puppeteer requires a headless Chromium in the Docker image, adding image size/build time — accepted as a reasonable cost for genuinely producing both formats; noted candidly in `docs/SYSTEM-DESIGN.md` if it becomes a real friction point.
- `low_confidence` chunks still surface in citations (with the warning) rather than being silently dropped, so a hiring manager can judge for themselves — consistent with the "grounded, never guessing" principle applied to OCR uncertainty, not just LLM uncertainty.
- **Real confidence values against all 5 scanned-CV fixtures** (`RENDER_SCALE = 2.0`, no image preprocessing): cv-002 → 61 (`low_confidence`), cv-007 → 77, cv-014 → 86, cv-022 → 77 (all three `confident`), cv-025b → 0 (`unusable`, never indexed — lands on `needs_ocr` instead, exactly as designed). See `docs/SYSTEM-DESIGN.md`'s gap table for the completeness caveat these numbers hide: tesseract's confidence is a mean over only the words it actually detected, not a page-completeness score, and on 4 of these 5 (deliberately low-contrast) fixtures it detects only the highest-contrast top line (name/title/email) — the rest of the page's text sits at a local contrast tesseract doesn't segment as text at all. A per-pixel global contrast-stretch preprocessing pass was tried and tested against all 5 fixtures; it did not increase how much of the page was detected (still header-only) and measurably hurt one fixture (cv-002: 61 → 0), so it was not adopted — disclosed here rather than silently attempted and abandoned.
- **This OCR-completeness gap directly caused a real evidence-grounding bug**, discovered live against `cv-014-heba-roshdy`'s single 54-character chunk: the Evidence Extractor's original grounding check only verified a cited chunk id was real, not that the cited evidence text actually came from it. See ADR-0006's "Evidence-grounding mechanism" section for the fix and its own residual risk (a model can still satisfy mechanical grounding by quoting real-but-irrelevant text) — Phase 5's OCR work is what made this provable, not what caused the underlying gap.
- **`generate_report`'s PDF integration test launching Puppeteer twice in one `node --test` run** (once to probe launchability for a dynamic skip, once for the real render) reliably broke the shared test file's knex/pg connection pool with an "Unable to acquire a connection" error — not reproducible via a plain Node script running the identical sequence, only under the test runner. Fixed by launching Chrome exactly once: the real `generate_report` call itself doubles as the launchability probe, with a launch failure caught and turned into a dynamic `t.skip()`. Noted here as a real, if narrow, `node --test` + Puppeteer interaction rather than silently worked around.
- **Live-verified `generate_report` end-to-end against a real degraded run**: a real DOCX (10,941 bytes) and PDF (91,157 bytes, 3 pages) generated for a genuine `data-analyst` screening run, with a real citation resolving to `cv-014-heba-roshdy, p.1` and the degraded-run banner correctly rendered. That run happened to reproduce ADR-0006's disclosed evidence-grounding residual risk live (CAND-014 scored 4/5 across all 7 competencies from one fabricated-looking rationale citing the same contact-info chunk) — kept as the verification artifact rather than re-run until it looked clean, since a report correctly displaying real (if disclosed-imperfect) data is a more honest demonstration than a cherry-picked one. See `docs/SECURITY.md` for the resulting note that the citation column shows document/page, not the quoted snippet text — a real limit on how easily a hiring manager can catch this from the report alone.
