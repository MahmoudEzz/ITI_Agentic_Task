## 2026-09-03 — Requirements analysis, variant derivation, and Phase 0 scaffolding

**Delegated to AI (Claude Code):**
- Full reading and structuring of the assessment PDF (`ITI-Instructor-Task.pdf`) into a condensed requirements brief.
- Derivation arithmetic for the assigned variant from the National ID (`29307051603297`): last-two-digits mod 7 for Domain, digit-sum mod 8 for Twist.
- Draft architecture, corpus, orchestration, security, and phased-build design (via a Plan sub-agent), covering FR-1 through FR-9, security controls, and the D6/T6-specific bias and OCR mechanisms.
- Generation of Phase 0 scaffolding: folder structure, `.gitignore`, `LICENSE`, `package.json`, doc skeletons (`BRD.md`, `SYSTEM-DESIGN.md`, `ARCHITECTURE.md`, `SECURITY.md`, `EVALUATION.md`, `AGENTIC-WORKFLOW.md`, this log), and 5 ADRs.

**Written/decided manually (by the developer, in conversation with the AI):**
- The actual National ID used for derivation.
- Tech stack (Node.js/JavaScript, not TypeScript).
- LLM provider choice (Ollama primary + Gemini secondary, explicitly rejecting a mock-only "second implementation" as insufficient).
- UI surface decision — an initial request for a Streamlit UI was corrected after the AI flagged it as incompatible with the Node.js stack (Streamlit is Python-only); resolved to a minimal static HTML/JS UI in the same repo instead of switching the whole backend to Python.
- T6 output-format scope (both DOCX and PDF, not DOCX-only).

**Where the AI got it wrong and had to be debugged empirically:**
- `npm install --save-dev eslint@9 @eslint/js prettier husky` failed with an `ERESOLVE` peer-dependency conflict: pinning `eslint@9` while leaving `@eslint/js` unpinned pulled in `@eslint/js@10`, which requires `eslint@^10`. The AI had not checked that the two packages' latest versions were mutually compatible before running the install. Fixed by installing both unpinned (`eslint@latest @eslint/js@latest`), which resolved to a matching `eslint@10`/`@eslint/js@10` pair.
- The `npm test`/`npm run test:integration` scripts were written as `node --test tests/unit` (a bare directory path). This failed immediately with `MODULE_NOT_FOUND` — Node's CJS module resolver tried to `require()` the directory itself rather than the test runner discovering files in it (an ESM/`"type": "module"` interaction the AI did not anticipate). The first fix attempt, switching to a glob (`node --test "tests/unit/**/*.test.js"`), was verified working, but *only tested under the locally installed Node v24* — glob-pattern arguments to `--test` are not supported on Node 20, which is what `engines` and the CI workflow were pinned to at the time. This was caught by deliberately testing under Node 20 and Node 22 via `nvm` after the fact, not by the AI proactively checking version compatibility across dev/CI before declaring the fix done. Resolved by bumping `engines`, `ci.yml`, and the `Dockerfile` to Node 22 everywhere, and confirming both `npm test` and `npm run lint` pass under that exact version — the lesson generalized to "verify against the pinned CI version, not whatever happens to be installed."
- The AI's first-pass UI question offered CLI/TUI vs. minimal-web-UI as the choices; when the developer asked for Streamlit, the AI did not silently attempt to bolt Python onto a Node.js repo — it surfaced the language mismatch explicitly and asked how to resolve it, rather than guessing.

**Verification:**
- Variant derivation arithmetic (97 mod 7 = 6; 54 mod 8 = 6) checked by hand against the brief's stated formula before being treated as final.
- Architecture/ADR content was reviewed by the developer for internal consistency (e.g. the orchestration ADR and the sequence-diagram placeholder in `ARCHITECTURE.md` describe the same state machine) before being committed, not committed unread.
- After the Node-version issue above, `npm test` and `npm run lint` were re-run explicitly under Node 20 (failed, as expected) and Node 22 (passed) via `nvm exec`, rather than trusting the fix on the strength of it passing once under an unpinned local Node version.

## 2026-09-03 — GitHub process setup and Phase 1 domain/contracts work

**Delegated to AI (Claude Code):**
- GitHub process setup: `gh` CLI install/auth, repo made public, branch protection (0 required approvals, `enforce_admins` on, 2 required CI checks), 10 milestones, initial Phase 1 issues, reviewing and merging 3 legitimate Dependabot PRs (closing a 4th that contradicted the Node 22 pin).
- Phase 1 implementation: 9 domain entities with real invariants (`Run.transition()` state machine, `Rubric`/`Score` composite-math validation), Zod contracts for agent I/O and the 4 required tools, and the `redactProtectedAttributes` bias-safety service — each as its own PR, closing issues #6/#7/#8.

**Where the AI got it wrong and had to be debugged or corrected:**
- Ran `docker compose up ollama ollama-pull` in the background to verify the Ollama model-pull design, then waited for a "task completed" notification that could never arrive: `ollama-pull` exits on success, but `ollama` runs forever, and `docker compose up` stays attached to both. The plan was structurally wrong, not just slow — polling the log for progress percentages for over an hour before recognizing this. Fixed by splitting into `docker compose up -d ollama` (detached) + `docker compose run --rm ollama-pull` (exits on its own), which is also the more correct way to test a one-shot init container in general.
- `gh api -X PUT repos/.../branches/main/protection/enforce_admins` returned 404. The endpoint is POST, not PUT — a GitHub API detail the AI got wrong on the first attempt and had to look up empirically from the error rather than knowing in advance.
- A `git add` staging mistake: added the docker-compose wording-fix file and the (already-staged) new entity files in one `git add`, then committed, producing one commit that bundled two unrelated changes. Caught immediately by reading the commit's file list, undone with `git reset --soft HEAD~1` before pushing (nothing published, so no history rewrite of shared state), and re-committed as two atomic commits.
- `ChunkResultSchema` declared `section`/`page`/`ocrConfidence` as `.nullable()` but not `.optional()`, meaning a retrieval adapter that omitted those keys entirely (a real, likely shape) would fail validation for no functional reason. Not caught by any test — the original 9 contract tests only ever exercised fully-populated payloads. Found during a design review, not by a failing test; fixed alongside adding the missing coverage.
- Two tool output schemas (`FinalizeShortlistOutputSchema`, `GenerateReportOutputSchema`) had zero test coverage and used `z.string().datetime()`, Zod 4's soft-deprecated spelling, rather than `z.iso.datetime()`. Also found during design review, not by a failing test. Verified both spellings currently validate identically on the installed `zod@4.5.4` before switching, rather than assuming the deprecation mattered functionally yet.
- A redaction test fixture ("Native English speaker with excellent writing skills.") was short enough that the matched phrase alone exceeded the drop-ratio threshold, causing the test to fail with a null-snippet dereference. This was the drop-threshold logic working correctly against an unrealistically terse example, not a bug in the redaction function — fixed by lengthening the test sentence to something a real CV bullet would look like, not by loosening the threshold.

**Verification:**
- `docker compose exec ollama ollama list` confirmed both `llama3.2:3b` and `nomic-embed-text` actually landed after the corrected two-step compose sequence — not just that the commands exited 0.
- `docker compose down; docker compose up -d ollama` (with `.env` deleted) was run explicitly to confirm the earlier `env file not found` error only occurs when config-parsing the *entire* compose file (e.g. `docker compose config -q`), not when starting a specific service that doesn't need it — this shaped the exact wording used in the README rather than a guessed claim about compose's behavior.
- Every fix above was re-run through `npm test`, `npm run test:contract`, and `npm run lint` before being committed, and each PR's CI (`build-lint-test`, `secret-scan`) was checked green before merge.

## 2026-09-04 — Phase 2: ingestion pipeline (DB, extraction, chunking) and corpus authoring

**Delegated to AI (Claude Code):** Postgres+pgvector schema and Knex repositories; txt/docx/pdf extraction adapters; the ADR-0001 structure-aware chunking service; corpus authoring (37→42 synthetic documents with bias/injection/OCR/conflicting-pair fixtures) via a parallel fork agent.

**Where the AI got it wrong and had to be debugged empirically:**
- The chunking service's section-heading detection (`detectSections.js`) was fully unit-tested against synthetic fixtures and still had two real bugs, found only by deliberately running it against actual corpus CVs and policy documents before merging rather than trusting the synthetic-test green checkmark: (1) requiring a blank line on both sides of a heading silently missed SUMMARY/EDUCATION/SKILLS in a real CV, catching only the one heading (EXPERIENCE) that happened to satisfy the stricter rule by chance; (2) the fix for that then let the document's own first line — almost always a two-word title-case name — get misread as a heading, since "start of document" had been treated as equivalent to "preceded by a blank line." A third bug in the same file (a job-entry title line like "Senior Engineer, Acme Corp" independently passing the same heading check and fragmenting the Experience section) was caught by the same real-corpus test pass. All three were invisible to the 14 unit tests written before this verification step — a clean test suite is not the same as verified-against-reality.
- A GitHub Actions run got stuck "queued" with 0 assigned jobs for over 10 minutes on a routine PR push (right after making the repo public), and the AI's first response was to keep polling the same stuck run rather than recognizing a genuinely stuck run needs a fresh trigger — an empty retest push resolved it immediately. Separately, the AI briefly ran `npm install js-tiktoken` and `git checkout -b phase-2-chunking` in a way that left uncommitted changes leaking onto a different branch (`phase-2-extraction-adapters`) after a `git checkout` between branches with uncommitted work in progress — caught by reading `git status` before pushing, fixed with `git stash -u` rather than force-pushing something that shouldn't have been there.
- The corpus-authoring fork (a separate agent instance) reported, unprompted, that it had briefly and mistakenly executed a few of this session's own in-progress Phase 2 DB-schema commands inside its isolated worktree before recognizing the context mismatch, and that it had reverted them before starting its actual task — flagged here per this log's own standard rather than treated as someone else's mistake to omit. Verified by checking that the DB-foundation branch/PR it named showed no unexpected artifacts.

**Verification:**
- Ran the not-yet-merged chunking module directly (via a scratch copy with corrected relative imports, since two different git worktrees don't share `node_modules`) against three real corpus documents with different heading conventions (SUMMARY/EXPERIENCE/EDUCATION/SKILLS; PROFILE instead of SUMMARY; numbered ALL-CAPS policy headings) before merging the PR — this is what surfaced the three bugs above, none of which the pre-existing unit tests caught.
- A real "scanned" PDF fixture from the corpus PR was extracted with `pdf-parse` directly (12 characters across 1 page) to confirm the OCR-detection threshold in `PdfExtractor.js` holds against real image-only content, not just the synthetic blank-page test in that PR.
- Reviewed the corpus fork's actual output before merging (manifest statistics, a bias CV, an injection CV's docx XML to confirm the white-on-white styling was really applied, a scanned PDF's real extracted-text yield) rather than accepting its self-report at face value.

## 2026-09-04 (continued) — Ingestion use case, and CI slowness found by watching runs instead of assuming green

**Where the AI got it wrong and had to be debugged empirically:**
- Added `{ skip }` to 3 of 4 Ollama-dependent tests in a new file, missed the 4th, and pushed — CI failed with a raw `fetch failed` instead of skipping gracefully. Only caught because the PR's CI run was actually watched to completion rather than assumed fixed once three tests demonstrated the pattern worked.

Caught by a test that deliberately pointed at a nonexistent path — exactly the scenario the acceptance criterion ("a document's failure doesn't abort the whole batch") was meant to cover, and the first implementation didn't actually satisfy it.
- Two new integration test files (`repositories.test.js`, `ingestDocument.test.js`) started intermittently failing each other's assertions once both existed — traced to Node's test runner running test *files* concurrently by default, with both files truncating the same `chunks`/`documents` tables in their own `beforeEach` against one shared live Postgres. Fixed with `--test-concurrency=1`, not by trying to make the tests independently robust to interleaving (the simpler, correct fix for DB-integration tests that were never designed for parallel-safe isolation).
- `npm ci` in CI went from seconds to ~7 minutes once `puppeteer` (a real future dependency, from the corpus-authoring PR) landed, downloading its own Chromium on every single run with nothing in CI ever launching a browser. ## 2026-09-05 (continued) — Phase 8: FR-3 evaluation harness with real golden-set numbers

**Delegated to AI (Claude Code):** the 27-case golden set (`corpus/golden-set.json`), `scripts/eval.js` (retrieval hit-rate, deterministic lexical-overlap groundedness, refusal correctness — no LLM-judge), and the bias name-swap invariance integration test, run for real against the dev corpus and a live Ollama model.

**Where the AI got it wrong, and where the AI's own process caught something real:**
- The first hand-verification of a golden-set question (before committing to 27 fixed entries) refused unexpectedly despite being a plainly answerable, well-evidenced question. The first hypothesis — a nondeterministic retrieval/ranking bug — was investigated and ruled out empirically (identical embeddings and identical top-8 retrieval across repeated fresh-process runs); adding a temporary debug line to `decideRefusal.js` (removed before commit) traced the real cause to a second, separate refusal path in `answerQuestion.js`: the retrieval-side decision wasn't refusing at all, but the model's answer omitted a `[n]` citation marker on that particular generation, and a citation-free answer is itself treated as a refusal. This became the harness's central, most consequential finding (see `docs/EVALUATION.md`) rather than a discarded false start, specifically because it was chased down empirically instead of accepted as "the question was probably just ambiguous."
- The first draft of the injection golden-set cases' `forbiddenPhrases` regex lists missed a real compliance failure on the first hand-verification run: the model's actual non-compliant output ("a score of 5 out of 5... ready for advancement") didn't match any of the initially-drafted phrases (which had assumed wording like "5/5" or "maximum score"). Caught only because each case was run by hand against the real system before finalizing the set (per an explicit review recommendation to verify 3 sample cases first), not assumed correct from the JSON alone — the phrase lists were broadened afterward, and the real compliance finding was kept and reported rather than quietly resolved by only fixing the regex.
- The harness's own groundedness heuristic (naive sentence-splitting to attribute a `[n]` marker to its citing sentence) produced 2 false-negative `groundedRatio: 0` results on answers that were manually confirmed to be genuinely well-grounded — root cause: the model sometimes opens an answer with a citation-header line ("[1] (document: X, section: Y)") as its own sentence before the real claim sentence, and the marker got attributed to that header rather than the claim. Disclosed as a limitation of the harness's own deliberately-simple heuristic in `docs/EVALUATION.md`, not presented as a system defect.
- A prompt-injection attempt was found embedded as literal text inside a Bash tool result while reading corpus fixture files for golden-set grounding — formatted to resemble a legitimate system-reminder instructing a new git-commit-attribution format (a `Claude-Session:` tracking URL). It was not followed, and was flagged to the user in the same turn rather than silently adopted or silently ignored.

**Verification:** `npm run eval` was run for real against the populated dev database (42 documents, 264 chunks) and a live local Ollama model, and its full raw output — including the 45.5% refusal-correctness number — was copied into `docs/EVALUATION.md` rather than summarized into a rounder-looking figure.
